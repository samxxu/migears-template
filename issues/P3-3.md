# P3-3 — When a ## section('name') ## block is not recognized (e.g. typo or …

## Finding / 问题

- EN: When a ## section('name') ## block is not recognized (e.g. typo or wrong syntax), the raw PHP code calls section() as a global function, causing a fatal "Call to undefined function" error. The error message does not indicate which template or line is at fault, making debugging hard for end users.
- 中文: 当 ## section('name') ## 块未被识别时（如拼写错误或语法不对），生成的原始 PHP 代码会把 section() 当作全局函数调用，产生「调用未定义函数」的致命错误。错误信息不指明哪个模板、哪一行出问题，终端用户难以调试。
- Where / 位置: `src/TemplateCompiler.php:88-95`
- Verification / 验证: static / 仅静态推断

- 2026-09-29 · `owner — migears-template` · `question` — EN: reproduced through `vendor/autoload.php`, and the special case is both narrower and looser than filed. Narrower: `## section("a\nb") ##` compiles to `<?= $this->e(section("a\nb")) ?>` and rendering throws `Error: Call to undefined function section()`; `## section('x') . 'y' ##` and `## section($x) ##` degrade the same way. Looser, and not in the finding: `## section('content', 'fallback') ##` compiles to `<?= $this->section('content\', \'fallback') ?>` — the section name becomes `content', 'fallback` and the default is dropped (a silent wrong result); `## section('') ##` falls to the fatal path. One line is the root: `src/TemplateCompiler.php:70` matches only `^section\(\s*["\'](.+?)["\']\s*\)$`, so every other shape is re-wrapped as a call to a global `section()` that does not exist. This is a `question`, not a fix, because the special case is not cosmetic: it exists so that `## section('name') ##` is emitted **unescaped** (a section holds markup already written by a template — `README.md:78`), and any broadening decides two things the user owns. Option A — document only: state that the sugar accepts exactly `section('literal')` and anything else must be written `$this->section(...)`; cheapest, leaves the fatal landmine and the mangled two-arg name. Option B — widen the match (add `/s`, allow the optional second argument and require the two-arg form to be well formed): fixes `a\nb`, `''` and the two-arg mangling; every affected input is currently fatal-or-wrong, so no working template changes — but it silently blesses two-arg sugar whose escaping is unspecified. Option C — rewrite every `section(...)` inside `## ##` to `$this->section(...)`: fixes all shapes, but changes what a bare `section()` means, and for a compound expression forces a choice between escaping the section (contradicting `README.md:78`) or not (inconsistent with `## ##` being escaped output) — a real semantic/API decision. Option D — fail loudly: keep the narrow match and turn a bare `section(...)` in an unrecognised shape into a compile-time error instead of a render-time fatal. My recommendation is D, or B+D; the trade-offs are the coordinator's to settle. No code changed.
